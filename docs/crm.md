# CRM-заявки

## Модель данных

`leads` хранит заявку, её пользователя, источник, статус и необязательного
назначенного менеджера. Допустимые статусы: `new`, `contacted`, `qualified`,
`converted`, `lost`; начальный статус по умолчанию — `new`. Поля `created_at`,
`updated_at`, `qualified_at` и `converted_at` хранятся с часовым поясом;
время квалификации и конверсии может отсутствовать. Источник обязателен и не
может состоять только из пробельных символов.

Необязательная `referral_attribution_id` связывает заявку с атрибуцией того же
пользователя: это проверяется внешним ключом PostgreSQL. Заявку можно создать
без атрибуции. Связанные пользователь, атрибуция и назначенный пользователь не
могут быть удалены, пока на них ссылается заявка.

`lead_status_history` хранит предыдущий и новый статусы, пользователя-автора
и время изменения. Предыдущий статус может быть `null` для записи о создании;
одинаковые предыдущий и новый статусы запрещены. История ссылается на заявку и
автора без каскадного удаления. Индексы подготовлены для поиска заявок по клиенту,
статусу, менеджеру и времени, а также для чтения истории и поиска по атрибуции.

На уровне этой схемы внешний ключ менеджера проверяет существование пользователя,
но не его роль. Политика работы менеджера с заявками, проверка назначения,
разрешённые переходы и защита от повторной конверсии будут реализованы в сервисном
слое на следующих задачах. Вставка записей напрямую в базу не создаёт историю
автоматически; все прикладные операции должны сохранять её в одной транзакции.


## Создание заявки

`POST /api/v1/leads` требует access-токен и принимает JSON с обязательным полем
`source` (непустая строка до 128 символов; крайние пробелы удаляются). Любой
авторизованный пользователь создаёт заявку только для себя: `user_id`, статус,
менеджер и реферальная атрибуция клиентом не задаются. Создание от имени другого
пользователя в текущем API не поддерживается.

Сервис автоматически связывает заявку с существующей атрибуцией пользователя,
если она есть на момент создания. `source` указывает источник, переданный клиентом,
и сам по себе не подтверждает реферальное происхождение; для этого используется
`referral_attribution_id`. Если атрибуция появится позже, ранее созданная заявка
автоматически не меняется. Одновременно создаются заявка со статусом `new` и запись
истории с `previous_status = null`, `new_status = new` и автором-пользователем.
Обе записи сохраняются одной транзакцией.

Для безопасного повтора можно передать заголовок `Idempotency-Key` со случайным
UUID версии 4. Первый запрос возвращает 201; повтор с тем же ключом и теми же
нормализованными данными — 200 и текущее состояние созданной заявки. Повтор с
другим `source` возвращает 409. Ключ действует в пределах пользователя и хранится
вместе с заявкой; совпадающие ключи разных пользователей независимы. Без ключа каждый
запрос создаёт отдельную заявку, даже при одинаковых данных. Значение ключа и хеш
исходного запроса не включаются в ответ.

## Просмотр заявок

`GET /api/v1/leads` возвращает страницу `items`, `limit`, `offset`; `limit` от 1 до
100, по умолчанию 20. Доступны фильтры `status`, `manager_id`, `date_from`, `date_to`
и сортировка по времени создания `sort=asc|desc` (по умолчанию `desc`), при равном
времени используется UUID. Границы времени требуют часовой пояс; период полуоткрытый
`[date_from, date_to)`. При изменении данных между запросами страницы с `offset`
могут сдвигаться.

`GET /api/v1/leads/{id}` возвращает доступную заявку. Клиент видит свои заявки,
менеджер — только назначенные ему, администратор — все. Эта политика также действует
для заявок, созданных сотрудниками: менеджеру доступна его собственная заявка только
после назначения на неё. Чужая или отсутствующая заявка возвращает 404. История
статусов в этих ответах не включена.
