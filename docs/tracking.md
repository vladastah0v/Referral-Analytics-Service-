# Интеграционные события

## Доступ и ключи

`POST /api/v1/events` и `POST /api/v1/events/batch` принимают заголовок
`X-Integration-Key`. Пользовательские JWT не дают права отправлять события. Ключ
привязан к одному `source_system`; источник определяется сервером, и передать его
в теле нельзя. Он выдаёт право только на отправку поддерживаемых событий.

В защищённом интерактивном терминале доступна команда:

```bash
docker compose exec api python -m app.cli create-integration --source shop
```

Ключ показывается один раз; храните его в менеджере секретов и не передавайте в
логи или URL; передавайте его только по HTTPS. Первую часть ключа до точки (UUID) используйте для отзыва:

```bash
docker compose exec api python -m app.cli disable-integration --id UUID
```

После отзыва новые запросы с ключом отклоняются. Уже принятые события остаются в
очереди. Для смены ключа создайте новый для того же источника и отключите старый.

## Формат событий

Тело одного запроса содержит `external_event_id`, `event_type`, `occurred_at` и
`payload`. `external_event_id` уникален в рамках источника. Время указывается с
часовым поясом, принимаются даты с 2000 года до текущего времени плюс пять минут.
Денежные значения передаются строками Decimal, не более двух знаков после запятой;
сумма заказа и финансовых операций должна быть положительной. Валюта — три
заглавные латинские буквы. Поля payload зависят от типа:

- `order_created`: `external_order_id`, `user_id`, `total_amount`, `currency`;
- `order_paid`, `order_refunded`: `external_order_id`, `operation_id`, `amount`, `currency`;
- `order_adjusted`: поля финансовой операции и `direction` со значением `credit` или `debit`;
- `order_cancelled`: `external_order_id`.

`operation_id` должен стабильно обозначать конкретную оплату, возврат или
корректировку, независимо от идентификатора доставки события. Поля других типов
событий, произвольные дополнительные поля и клиентский `referrer_id` отклоняются.

Уведомления о переходах, регистрациях и лидах подтверждают факты, записанные через API сервиса. Передайте идентификатор и точное время из ответа соответствующего API. Сервис сравнивает моменты времени с учётом часового пояса и точности до микросекунд.

| Тип | Поле payload (UUID) | Значение для occurred_at |
| --- | --- | --- |
| `referral_clicked` | `click_id` | `clicked_at` перехода |
| `user_registered` | `user_id` | `created_at` пользователя |
| `lead_created` | `lead_id` | `created_at` лида |
| `lead_qualified` | `lead_id` | `qualified_at` лида |

Для сбора аналитики достаточно самой бизнес-операции. Доставка подтверждения с отдельным внешним идентификатором сохраняет запись в журнале событий. Исходный переход, пользователь или лид учитывается один раз.

Новый запрос возвращает 202 с идентификатором и статусом `pending`. Идентичный повтор возвращает 200,
повтор с тем же идентификатором и другими данными — 409. Ключи интеграций с одним
источником разделяют область уникальности событий.

`POST /api/v1/events/batch` принимает `{"events": [...]}` из 1–100 объектов и
возвращает 207 со списком `results` в исходном порядке. Каждый объект сохраняется
в отдельной транзакции: `status_code` равен 202 для нового, 200 для повтора, 409
для конфликта, 422 для ошибки валидации. При неожиданной ошибке сервера ранее
сохранённые элементы не откатываются; повторите пакет с теми же идентификаторами.

## Обработка и ошибки

Запись события и запись outbox фиксируются одной транзакцией. Celery beat
периодически запускает worker, который выбирает доступные записи с блокировкой
`SKIP LOCKED`. Финансовый результат, статус события и состояние outbox сохраняются
в одной транзакции. Доставка может быть повторной; бизнес-эффекты защищаются
идентификаторами финансовых операций и ограничениями базы, без гарантии exactly-once.

Если заказ, оплата или подтверждаемый факт ещё отсутствуют, воркер назначает следующую попытку с экспоненциальной задержкой до пяти минут. После 10 попыток событие получает статус `rejected` и код `prerequisite_timeout`. Поле `last_error` сохраняет конкретную причину ожидания, например `fact_missing`. Расхождение времени с существующим фактом сразу даёт `fact_time_conflict`.

При непредвиденной ошибке обработки воркер откатывает изменения этого события и назначает повтор. После 10 попыток код ошибки — `processing_error`. Если сама транзакция не смогла зафиксироваться, событие остаётся доступным для следующего запуска.

Администратор видит результат, число попыток и последнюю причину через `GET /api/v1/events/{id}`. Менеджер видит заказы клиентов с назначенной ему заявкой, подтверждённые регистрации таких клиентов и подтверждённые события назначенного ему лида. Доступ к событиям переходов есть только у администратора.

После устранения причины администратор сервиса может повторить обработку отклонённого события. Для исправленного payload отправьте новое событие с новым идентификатором.

```bash
docker compose exec api python -m app.cli retry-event --id UUID_СОБЫТИЯ
```

Расписание и диагностика описаны в [документации фоновых задач](workers.md).
