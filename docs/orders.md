# Заказы и финансовые операции

## Модель заказа

`orders` хранит идентификатор внешнего заказа и источника, пользователя, состояние,
сумму, валюту, даты и необязательную реферальную атрибуцию. Пара
`(source_system, external_order_id)` уникальна: одинаковые внешние идентификаторы
в разных источниках относятся к разным заказам. Допустимые состояния: `created`,
`paid`, `cancelled`, `partially_refunded`, `refunded`. Для оплаченного и обоих
состояний возврата обязательно `paid_at`.

`total_amount` хранится как `NUMERIC(14,2)` и не может быть отрицательным или NaN;
нулевая сумма допускается. Валюта — три заглавные латинские буквы. Внешний ключ
гарантирует, что выбранная атрибуция принадлежит покупателю. Для заказа без
атрибуции `referral_attribution_id` равен `null`.

`attribution_frozen_at` предназначен для фиксации момента принятия решения об
атрибуции: `null` означает, что решение ещё не зафиксировано; дата вместе с
`referral_attribution_id = null` позволяет зафиксировать отсутствие атрибуции.
Атрибуция не может быть указана без времени фиксации. Ограничения схемы проверяют
согласованность ссылок, но не делают запись неизменяемой: запрет последующего
изменения решения и исходной записи атрибуции должен обеспечивать сервис обработки
заказов.

## Финансовые операции

`order_financial_events` хранит отдельные финансовые операции, источник,
стабильный внешний идентификатор операции, сумму, валюту, время операции
`occurred_at` и время записи `recorded_at`. Виды операций:

- `payment` — подтверждённая оплата;
- `refund` — подтверждённый возврат;
- `adjustment_credit` — положительная корректировка;
- `adjustment_debit` — отрицательная корректировка.

Сумма каждой операции строго положительна, хранится как `NUMERIC(14,2)` и не
может быть NaN; знак влияния определяется видом операции. Валюта операции должна
совпадать с валютой заказа, что проверяется составным внешним ключом. Удаление
заказа при наличии финансовых операций ограничено.

Пара `(source_system, external_financial_event_id)` уникальна. Источник должен
использовать один и тот же идентификатор для повторных сообщений об одной и той же
финансовой операции; идентификатор операции не должен подменяться идентификатором
доставки сообщения. Ограничение уникальности само по себе не распознаёт одну и ту же
операцию, ошибочно присланную под разными идентификаторами.

Проверка допустимых переходов состояний, сумм оплат и возвратов, порядка событий,
идемпотентная обработка повторов и расчёт выручки ещё не реализованы. Таблица не
запрещает обновление или удаление записей на уровне прав БД; сохранение истории
финансовых операций будет обеспечиваться сервисным слоем. Валидация точности до
записи в PostgreSQL и правило округления Decimal также относятся к обработке
финансовых событий. Создание и изменение заказов через публичное API не добавлено.
