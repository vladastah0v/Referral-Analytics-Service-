# Заказы и финансовые операции

## Модель заказа

`orders` хранит идентификатор внешнего заказа и источника, пользователя, состояние,
сумму, валюту, даты и необязательную реферальную атрибуцию. Пара
`(source_system, external_order_id)` уникальна: одинаковые внешние идентификаторы
в разных источниках относятся к разным заказам. Допустимые состояния: `created`,
`paid`, `cancelled`, `partially_refunded`, `refunded`. Для оплаченного и обоих
состояний возврата обязательно `paid_at`.

`total_amount` хранится как `NUMERIC(14,2)` и не может быть отрицательным или NaN;
нулевая сумма допускается. Валюта — три заглавные латинские буквы. Внешний ключ
гарантирует, что выбранная атрибуция принадлежит покупателю. Для заказа без
атрибуции `referral_attribution_id` равен `null`.

`attribution_frozen_at` предназначен для фиксации момента принятия решения об
атрибуции: `null` означает, что решение ещё не зафиксировано; дата вместе с
`referral_attribution_id = null` позволяет зафиксировать отсутствие атрибуции.
Атрибуция не может быть указана без времени фиксации. Ограничения схемы проверяют
согласованность ссылок, но не делают запись неизменяемой: запрет последующего
изменения решения и исходной записи атрибуции должен обеспечивать сервис обработки
заказов.

## Финансовые операции

`order_financial_events` хранит отдельные финансовые операции, источник,
стабильный внешний идентификатор операции, сумму, валюту, время операции
`occurred_at` и время записи `recorded_at`. Виды операций:

- `payment` — подтверждённая оплата;
- `refund` — подтверждённый возврат;
- `adjustment_credit` — положительная корректировка;
- `adjustment_debit` — отрицательная корректировка.

Сумма каждой операции строго положительна, хранится как `NUMERIC(14,2)` и не
может быть NaN; знак влияния определяется видом операции. Валюта операции должна
совпадать с валютой заказа, что проверяется составным внешним ключом. Удаление
заказа при наличии финансовых операций ограничено.

Пара `(source_system, external_financial_event_id)` уникальна. Источник должен
использовать один и тот же идентификатор для повторных сообщений об одной и той же
финансовой операции; идентификатор операции не должен подменяться идентификатором
доставки сообщения. Ограничение уникальности само по себе не распознаёт одну и ту же
операцию, ошибочно присланную под разными идентификаторами.

## Обработка заказов

Заказы создаются и изменяются только доверенными интеграционными событиями,
описанными в `docs/tracking.md`. Источник заказа — источник авторизованного ключа;
`(source_system, external_order_id)` определяет заказ. При первом создании
сервис фиксирует атрибуцию пользователя, действовавшую на время создания заказа,
в том числе её отсутствие. Следующие события не меняют это решение.

Для текущей интеграции сумма заказа должна быть положительной; поддерживается одна
полная оплата на сумму заказа. Нулевые заказы и оплата частями не поддерживаются.
Повтор одного и того же платёжного `operation_id` с теми же данными не создаёт
вторую финансовую операцию. Идентифицированный другой оплатой повтор для уже
оплаченного заказа отклоняется; в PostgreSQL также действует уникальное
ограничение одной оплаты на заказ.

Возвраты могут быть частичными или полными. Под блокировкой заказа проверяются
валюта, время операции и хронологический остаток с учётом подтверждённой оплаты,
возвратов и корректировок. Остаток не может стать отрицательным ни в одной точке
истории; при недостаточном остатке событие временно откладывается, поскольку
предшествующая положительная корректировка могла прийти позже. После лимита
повторов оно требует проверки администратором. При одинаковом времени сначала
учитываются оплата, затем положительные корректировки, затем остальные операции;
внутри группы используется UUID операции.

Если есть возврат и остаток равен нулю, заказ имеет статус `refunded`; если есть
возврат и остаток положителен — `partially_refunded`; без возвратов — `paid`.
Корректировка может изменить итоговый статус после возврата.

`created` можно отменить; отмена оплаченного заказа отклоняется — для него нужен
возврат. Оплата или возврат, пришедшие до создания заказа, и возврат до оплаты
откладываются и повторяются. Финансовая операция не может предшествовать созданию
заказа, возврат или корректировка — оплате. Поздние финансовые операции проверяются
по всей хронологической истории; конфликтные события, например оплата после уже
обработанной отмены, не переписывают состояние автоматически и требуют сверки.

Таблица финансовых операций не защищена от прямого изменения правами базы данных;
прикладной обработчик добавляет операции и не изменяет существующие. Поэтому доступ
к записи в финансовые таблицы следует ограничивать сервисным пользователем БД.

## Доступ к заказам

`GET /api/v1/orders` и `GET /api/v1/orders/{id}` требуют JWT. Клиент видит свои
заказы, администратор — все. Менеджер видит заказы клиентов, у которых есть хотя бы
одна назначенная ему заявка, независимо от её статуса; это включает другие заказы
этого клиента. Недоступный заказ возвращает 404. Список поддерживает `status`,
`currency`, `limit` (1–100) и `offset`, отсортирован по времени получения заказа
`created_at` и UUID по убыванию.

## Выручка

`GET /api/v1/analytics/revenue` доступен администратору и менеджеру с той же
областью клиентов, что у списка заказов. Результаты группируются по валютам;
конвертация и сложение разных валют не выполняются. Необязательный фильтр
`currency` задаёт валюту, `date_from` и `date_to` — полуоткрытый интервал UTC
`[date_from, date_to)` по `occurred_at` финансовой операции.

Для каждой валюты `gross_revenue` — оплаты плюс положительные корректировки;
`refunds` — возвраты, `adjustments_debit` — отрицательные корректировки;
`net_revenue` — валовая сумма минус возвраты и отрицательные корректировки.
`referral_attributed_revenue` рассчитывается тем же способом для заказов с
зафиксированной атрибуцией. `paid_orders` — число различных заказов с оплатой в
интервале. Суммы возвращаются десятичными строками с двумя знаками. Периодные
показатели отражают операции периода, а не когорту заказов: при возврате за ранее
оплаченный заказ чистая выручка периода может быть отрицательной.

## Миграция существующих данных

Миграция `b99bb4d96baa` добавляет время внешнего создания заказа и ограничение
одной оплаты. Если в базе уже есть несколько оплат одного заказа, проведите их
сверку перед обновлением. Миграция сохраняет финансовые записи.

Миграция `20261123_01` заполняет отсутствующий `external_created_at` по самой ранней
из записанных дат заказа и его финансовых операций. Это оценка по имеющимся данным.
Если источник сообщает о событии раньше этой даты, проверьте хронологию по данным
источника перед повторной обработкой. Ранее отклонённые события можно вернуть в
очередь командой `retry-event` после сверки.

Для новых корректировок используется общий идентификатор операции независимо
от направления. Идентификаторы старых операций и исторические суммы сохраняются.
Если раньше были приняты две разнонаправленные записи с одним внешним
идентификатором, сверяйте их с журналом источника перед корректировкой остатков.
