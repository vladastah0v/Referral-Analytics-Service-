# Реферальная воронка

Администратор получает отчёт по всем реферальным кодам через
`GET /api/v1/analytics/referrals`. В ответе только агрегаты. Владелец кода может
посмотреть свои показатели через `GET /api/v1/referrals/statistics`.

| Поле | Что измеряет | Время события |
| --- | --- | --- |
| `total_clicks` | Число записанных переходов | `referral_clicks.clicked_at` |
| `unique_visitors` | Число различных `visitor_id` среди этих переходов | `referral_clicks.clicked_at` |
| `referred_registrations` | Число регистраций с зафиксированной реферальной атрибуцией | `referral_attributions.attributed_at` |
| `conversion_rate` | Регистрации / уникальные посетители × 100, строка с двумя десятичными знаками, округление ROUND_HALF_UP | Обе выборки за указанный период |

Если посетителей нет, конверсия равна `null`. Регистрация может попасть в период,
даже если исходный клик был раньше. Поэтому конверсия за период может превышать 100%.

Границы `date_from` и `date_to` принимают дату и время с часовым поясом. Начало
включается, конец исключается. Любую границу можно опустить. Фильтры `campaign`,
`source` и `referral_code` задаются совместно, сравнение точное и чувствительно
к регистру. Для регистрации берутся значения атрибутированного клика.
История отключённых кодов входит в расчёт.

При `group_by=day|week|month` поле `periods` содержит интервалы с событиями в
порядке возрастания. Границы календарные, в UTC, неделя начинается в понедельник.
Без группировки `periods` пуст. Верхний уровень всегда показывает итоги за весь
выбранный диапазон. Посетитель, пришедший в разные дни или по разным кодам,
учитывается один раз в итоге и один раз в каждом соответствующем интервале.

## CRM-воронка

`GET /api/v1/analytics/funnel` показывает, сколько заявок дошло до квалификации
и конверсии в CRM. Администратор видит все заявки, менеджер — только назначенные
ему на момент запроса. Переназначение меняет область видимости и для прошлых периодов.

| Поле | Правило расчёта |
| --- | --- |
| `total_leads` | Число заявок с датой создания в диапазоне `[date_from, date_to)`. Каждый лид одного клиента учитывается отдельно. |
| `qualified_leads` | Из отобранных заявок — число имеющих `qualified_at` до верхней границы. Сюда входят и заявки, потерянные после квалификации. |
| `converted_leads` | Из тех же заявок — число имеющих `converted_at` до верхней границы. Источником служит переход CRM в статус `converted`. |
| `lead_conversion_rate` | `converted_leads / total_leads × 100`, десятичная строка с двумя знаками, округление `ROUND_HALF_UP`. При пустой выборке значение равно `null`. |

Границы необязательны, принимают время с часовым поясом и возвращаются в UTC.
Без `date_to` учитываются все сохранённые переходы выбранных заявок.
При `group_by=day|week|month` заявки разбиваются по **дате создания**, неделя
начинается в понедельник. Для всех групп действует общая верхняя граница отчёта.
Например, для январского отчёта заявка от 5 января с конверсией 20 января попадёт
в число конвертированных за группу 5 января. Конверсия 1 февраля в этот отчёт
не попадёт. Пустые группы пропускаются. Без группировки список `periods` пуст.

`source` сравнивается с источником самой CRM-заявки. Фильтры `campaign` и
`referral_code` используют атрибуцию, привязанную к заявке при создании.
Заявки без атрибуции входят в общий отчёт и могут отбираться по `source`.
Все заданные фильтры применяются совместно, строки сравниваются с учётом регистра.

## Сводный отчёт

`GET /api/v1/analytics/overview` доступен администратору. Ответ объединяет
реферальные метрики (`referrals`), показатели CRM (`funnel`), выручку
(`revenue`) и начисления вознаграждений (`rewards`) по валютам. Все разделы читаются из одного снимка PostgreSQL.

Параметры `date_from`, `date_to` задают полуоткрытый период в UTC. Для переходов,
регистраций и заявок действуют правила соответствующих отчётов выше. В финансовом
разделе границы применяются к времени финансовой операции `occurred_at`.
Количество оплаченных заказов, выручка и возвраты рассчитываются по правилам
[отчёта о выручке](orders.md#выручка). Дополнительное поле `average_order_value`
содержит сумму подтверждённых оплат, делённую на число оплаченных заказов в той
же валюте за тот же период. Результат округляется до двух знаков. Если за период
были только возвраты или корректировки, средний чек равен `null`.

`campaign` и `referral_code` отбирают реферальные события и связанные с ними
заявки и заказы через сохранённую атрибуцию. Для финансовых показателей
используется зафиксированная атрибуция заказа. Фильтр `source` применяется
к источнику клика для реферальных и финансовых показателей и к полю источника
самой заявки для CRM. Поэтому один и тот же фильтр может дать разные наборы
каналов в разделах. Без этих фильтров в финансовую и CRM-части входят также
прямые заказы и заявки.

С `group_by=day|week|month` каждый элемент `periods` содержит эти разделы за
соответствующий календарный интервал UTC. Интервал присутствует, если данные
есть хотя бы в одном разделе. Для отсутствующих данных счётчики равны нулю,
конверсии — `null`, финансовый список пуст. Верхний уровень содержит расчёт
за весь диапазон, включая уникальных посетителей и средний чек за весь период.
Без группировки `periods` пуст.

## Рейтинг рефереров

Администратор получает рейтинг через `GET /api/v1/analytics/top-referrers`.
Каждая строка относится к одному рефереру (`referrer_id`) и одной валюте.
В выборку попадают финансовые операции по заказам с зафиксированной
реферальной атрибуцией. Несколько кодов одного реферера дают одну строку в валюте.

`net_revenue` — сумма оплат и кредитовых корректировок за вычетом возвратов
и дебетовых корректировок. Денежное значение возвращается строкой с двумя
знаками. `paid_orders` — число различных заказов с оплатой внутри периода.
Если за выбранное время был только возврат, реферер попадёт в рейтинг
с отрицательной выручкой и нулём оплаченных заказов.

`position` начинается с 1 в каждой валюте. Сначала идут большие суммы чистой
выручки, при равенстве — меньший UUID реферера. `limit` ограничивает число
строк **в каждой валюте** (от 1 до 100, по умолчанию 10). Фильтр `currency`
выбирает одну валюту, например `currency=KZT`.

Период `[date_from, date_to)` определяется по времени финансовой операции
в UTC. Границы необязательны. Фильтры `campaign`, `source` и `referral_code`
относятся к атрибутированному переходу и его коду и применяются совместно.
`items` содержит рейтинг за весь выбранный период. При `group_by=day|week|month`
поле `periods` дополнительно содержит самостоятельный рейтинг каждого календарного
интервала в UTC. Лимит действует отдельно внутри каждого интервала и валюты.
Без совпадений оба списка пусты.

## Сравнение конверсии

Администратор запрашивает `GET /api/v1/analytics/conversion` с обязательными
`date_from` и `date_to`. По умолчанию базой сравнения служит непосредственно
предшествующий интервал той же длительности в UTC. Чтобы выбрать другую базу,
передайте обе границы `previous_from` и `previous_to`. Предыдущий период должен
закончиться к началу текущего. Например, для сравнения двух календарных месяцев
разной длины укажите границы обоих месяцев явно.

В `previous` и `current` возвращаются реферальная и CRM-воронки со своими
числителями и знаменателями. К обеим применяются одинаковые фильтры
`campaign`, `source`, `referral_code` и группировка `group_by`. Для CRM
каждая когорта оценивается до конца своего периода. Поля `referral_change` и
`lead_change` сравнивают итоговые конверсии целых периодов. При изменении с 10%
до 15% поле `percentage_points` равно `"5.00"`, а `relative_growth_percent` —
`"50.00"`. Относительный рост равен разнице ставок, делённой на предыдущую ставку,
умноженной на 100. Расчёт использует исходные количества, итог округляется
до сотых методом ROUND_HALF_UP. При отсутствии знаменателя в любой воронке
обе разницы равны `null`. При определённой, но нулевой предыдущей ставке
только относительный рост равен `null`.

Пример запроса для отчёта за январь со сравнением с декабрём:

```http
GET /api/v1/analytics/conversion?date_from=2026-01-01T00:00:00Z&date_to=2026-02-01T00:00:00Z
```

## Сумма вознаграждений

В `/overview` поле `rewards` содержит строки `currency` и `total_rewards`
для каждой валюты с изменениями суммы. Единица измерения — валюта вознаграждения.
Метрика показывает чистое начисление за период по времени записи версии
`referral_reward_history.created_at`. Для каждой версии из суммы вычитается
сумма предыдущей версии того же вознаграждения (для первой — ноль).
Например, начисление 100 в январе и снижение до 60 в феврале дают +100 в январе
и −40 в феврале. Подтверждение суммы даёт нулевой вклад. Поэтому повторные
версии не удваивают начисления. Предыдущая версия учитывается и тогда, когда она записана до начала периода.
Группировка использует время версии, фильтры канала — сохранённую атрибуцию.
За всю историю результат равен сумме конечных значений вознаграждений с историей.

## Разрезы выручки

`/revenue` поддерживает `group_by=day|week|month`, `campaign`, `source`,
`referral_code` и `currency`. Итоги по валютам находятся в `items`,
календарные разрезы — в `periods[].items`. Канал определяется по зафиксированной
атрибуции заказа. Менеджеру доступны финансовые операции только в рамках его
текущей области доступа к заказам.

## Redis и свежесть отчётов

Все шесть административных и менеджерских отчётов используют Redis по адресу
`REDIS_URL`. Срок хранения задаётся через `ANALYTICS_CACHE_TTL_SECONDS`
(по умолчанию 60 секунд, 0 отключает кэш, максимум 3600 секунд). Если несколько
установок используют общий Redis, задайте каждой своё значение
`ANALYTICS_CACHE_NAMESPACE`. HTTP-ответ содержит `Cache-Control: private, no-store`.

Каждый запрос сначала проверяет сессию и роль в PostgreSQL. Ключ Redis учитывает
маршрут, все валидированные параметры, UUID пользователя, роль, пространство
имён установки, базу, схему, время запуска PostgreSQL и версию данных
аналитики. Отчёт читается в транзакции REPEATABLE READ.
Запрос, начавший чтение после фиксации изменения, видит новую версию данных,
включая изменения назначения менеджера. Дополнительная задержка обновления
из-за TTL отсутствует. Уже выполняющийся запрос завершится на своём снимке.

Версия — сумма счётчиков в `analytics_cache_revisions`. Триггеры изменяют
счётчики в транзакциях записи переходов, кодов, атрибуций, заявок, заказов,
финансовых операций, вознаграждений и истории начислений. Откат транзакции
откатывает её вклад в версию. Параллельные писатели используют свободные строки
счётчиков. Изменение любой из перечисленных таблиц обновляет версию для всех
отчётов, поэтому при частой записи доля попаданий может снижаться. Старые ключи
удаляются по TTL. Ошибка или тайм-аут Redis переключают запрос на PostgreSQL.
Бюджет ожидания Redis — 250 мс на чтение или запись. Перед запуском этой версии
приложения примените миграции командой `docker compose run --rm api alembic upgrade head`.

При восстановлении резервной копии базы в работающем кластере смените пространство
имён кэша, чтобы строки старого снимка с тем же номером версии не использовались.
